## Q2–Q7 답변

### Q2 — K2·K3는 조건부로 등가이나, 현재 문안만으로 모든 구현 결과의 등가성을 보장하지 못한다.

- **[측정] 수명:** 현재 세 변수는 `scope.launch` 안, collect 밖에 있다(C:630·647–652). `TickLoopState`도 같은 위치에서 매 launch마다 새로 만들면 수명이 같다. `start()`는 이미 활성 상태면 반환하므로 “start 호출마다”보다 “새 launch마다”가 정확하다(C:628).
- **[추론] 단일 대입의 경로 대응:** maintenance 2개는 banking 계산 전에 반환한다(C:667·673). 이후 정상 조기 종료 24개와 정상 끝 1개를 단계부의 정상 반환으로 모으면 공통 대입으로 치환할 수 있다. 중간에 새 suspend·catch·finally·취소 체크를 넣지 않아야 한다.
- **[측정] 처리된 예외:** publication의 일반 저장 예외는 null로 정상 반환되어 banking 대입을 한다(C:1286–1291 → 1044/1146). 반면 재던진 cancellation은 그 대입에 도달하지 않는다(C:1284–1285).
- **[추론] 반환 전파:** `?: run { return@collect }`의 `run`은 inline이다. 추출한 함수 안에서 `return`으로 치환하면 해당 함수 종료로 바뀐다. 여러 단계로 쪼갤 때 Abort를 호출자까지 명시적으로 전파해야 한다(C:822·1042·1100·1144).
- **[측정] captured state 세 가지:**
  - `cooldownFiredThisTick`은 두 쿨다운 단계에서 변경되어 escalation과 new-trigger를 억제한다(C:964·995·1019·1086·1134).
  - `popupShownThisTick`은 **성공한 overlay 회계 callback 안에서만** true가 된다(C:1112). 함수 진입이나 show 시도만으로 true 처리하면 안 된다.
  - `syncedSession`은 C:952에서 copy로 갱신되고 C:1137·1190에서 사용된다. 갱신 전 값을 다른 단계에 넘기거나 tracker 최신값으로 대체하면 의미가 달라진다. tracker의 mark 메서드도 기존 snapshot을 수정하지 않고 copy한다(`RiskSessionTracker.kt:348–363`).
- **[측정] suspend·훅:** publication뿐 아니라 navigation·notification commit·overlay show도 higher intent의 완료를 기다릴 수 있다(C:1330·1344·1368·1423). guardian 조회(C:588–589), cleanup hook(C:1455), downgrade hook(C:895), notification/accounting hook(C:1072·1104·1166·1182)의 상대 순서를 보존해야 한다.
- **[추론] 인자 선계산 금지의 구체 사례:** `bankingJustOpened`를 앞 단계에서 계산하면 C:967의 volatile 읽기가 앞당겨진다. `cooldownManager.isShowing()`을 공통 Boolean 인자로 만들면 C:948·1004·1086·1138의 분기별 재조회와 단락 평가가 사라진다. `clock()`도 C:727·760·866·1088·1139에서 각각 실행해야 한다.
- **[측정] 락 대상:** C:892의 `this@DefaultRiskDetectionCoordinator`를 state-holder의 `this`로 바꾸면 안 된다. K2 holder는 상태 보관용이어야 하며 락 소유 객체가 되어서는 안 된다.

### Q3 — 기술적으로 최소 공통화는 가능하지만, R1에서는 K6를 생략하는 편을 권고한다.

- **[측정] 경로 차이:** escalation은 publication·navigation·notification 뒤 popup 내부에서 debounce를 판정한다(C:1041–1089). new-trigger는 debounce 통과 후 event 생성·publication을 한다(C:1139–1144).
- **[측정] GUARDED:** `recordRiskEvent → post-push reset 검사`까지 수행하고 navigation 및 post-navigation 검사를 생략한다(C:1048–1066). 이후 nullable publication으로 notification commit은 계속한다(C:1072–1077·1373–1375). 이 분기를 “publication 없음=전체 Abort”로 합치면 안 된다.
- **[추론] 가능한 최소 helper:** **post-push reset 검사·exact cleanup → publication이 있을 때 navigation → post-navigation reset 검사·exact cleanup**만 `suspend Boolean` helper로 묶을 수 있다. 경로별 stage 문자열은 호출 지점의 리터럴로 전달하고 navigation 실패 로그는 지연 callback으로 남겨야 정적 Log 호출 수도 보존할 수 있다.
- **[추론] helper 밖에 남길 것:** publish/record 선택, debounce, notification commit과 회계, guardian 조회, accounting hook, show callback. 특히 `nowMs`는 guardian suspension 전에 캡처한 값을 그대로 회계에 사용해야 한다(C:1088·1110, 1139·1188).
- **[측정] 회계 차이:** escalation은 `triggers`를 마킹하고 popup flag를 변경한다(C:1111–1112). new-trigger는 `syncedSession.notifiedActiveThreats + newTriggers`를 마킹한다(C:1189–1190).
- **[추론] 권고 이유:** 이미 핵심 publication 효과 게이트가 C:1386의 helper로 공통화되어 있다. 그 위의 절차까지 합치려면 경로별 callback과 null 분기를 다시 주입해야 하므로, 이번 리팩터의 리뷰 표면을 충분히 줄인다고 보기 어렵다.
